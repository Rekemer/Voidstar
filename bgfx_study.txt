Yep—creating and deleting GPU stuff “at runtime” is exactly what bgfx is built for. Here’s how it stays sane:

The two tracks each frame
Resource commands (CPU-side “setup”): create/destroy/update texture/buffer/shader… These are serialized into the frame’s command buffers (m_cmdPre for before drawing, m_cmdPost for after).

Draw/dispatch commands: captured as RenderItems (RenderDraw / RenderCompute) that reference resources by handle (index into bgfx’s resource tables).

At bgfx::frame():

The app/submission side seals the frame (all encoders ended).

It flips frames: the sealed one becomes m_render (for the backend to consume), and a fresh m_submit opens for the next frame.

The render backend thread wakes up and:

Runs m_cmdPre → turns “CreateTexture/UpdateBuffer/…” into real API calls (vkCreateImage, vkCmdCopyBufferToImage, …). This happens before any draw of the frame.

Sorts RenderItems by view / program / depth and issues the actual Vulkan draws/dispatches.

Runs m_cmdPost (readbacks/screenshots/etc.) after drawing.

CommandBuffer& getCommandBuffer(CommandBuffer::Enum _cmd)
{
	CommandBuffer& cmdbuf = _cmd < CommandBuffer::End ? m_submit->m_cmdPre : m_submit->m_cmdPost;
	uint8_t cmd = (uint8_t)_cmd;
	cmdbuf.write(cmd);
	return cmdbuf;
}
